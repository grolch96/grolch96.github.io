Контекст и задача

Требовалось восстановить работоспособность устаревшей информационной системы (далее — «система») после выхода из строя физического оборудования. Система построена на базе Ubuntu 14.04, работает в кластерной конфигурации и содержит встроенные механизмы защиты от тиражирования — жёсткую привязку к аппаратному обеспечению.

Стандартные методы миграции (преобразование дисков, перенос в новую среду) не работали: при попытке загрузки возникали паника ядра и BSOD. Требовалось найти способ запустить систему в виртуальной среде, сохранив целостность кластера и данных.

Диагностика и выявленные зависимости

В ходе анализа бэкапа и тестового стенда были выявлены следующие взаимосвязи, критичные для стабильной работы системы:

  • Архитектура процессора — критическая зависимость (при несовпадении — немедленная перезагрузка).
  • Мосты материнской платы — аналогичная критическая зависимость.
  • Сетевые правила (iptables/firewall) — критическая зависимость.
  • Сетевые устройства — критическая зависимость: связь не должна быть разорвана, устройство не должно быть выключено.
  • Сетевая адресация (MAC-адреса) — жёсткая привязка как к логическим, так и к физическим адресам. При изменении MAC после импорта система повреждает сетевые конфиги.

Также на уровне ОС были обнаружены скрытые скриптовые механизмы (три ветви) и «спрятанные» правила фаервола, влияющие на поведение системы.

Решение 1: VMware — отрицательный результат

Первая попытка заключалась в последовательном исключении компонентов из конфигурации .vmx и замедлении загрузки для выигрыша времени:

  • Разработаны скрипты boot-delay.cmd (задержка загрузки) и clear-cache.cmd (очистка кэша проблемных правил).
  • Написаны аппаратные скрипты для хоста и новые конфиги виртуальной машины.
Результат: отрицательный. Даже при максимальном «раздевании» конфигурации система работала не более 2 минут, после чего следовал сбой. Метод был признан тупиковым.

Решение 2: VirtualBox — обход через импорт VMX

Ключевая идея заключалась в использовании механизма импорта конфигурации VMware (.vmx) в VirtualBox, который появился в VirtualBox относительно недавно. На момент создания системы защиты производитель не мог учесть эту возможность: тогда поддерживалось лишь прямое открытие виртуальных дисков (.vmdk), но не импорт всей разметки .vmx.

Таким образом, был найден не «взлом», а архитектурная брешь: система сопротивлялась конвертации дисков и прямому запуску, но не была рассчитана на то, что гипервизор в будущем научится «понимать» родную конфигурацию VMware. Это позволило опираться на источник проблемы, а не преодолевать его.

Шаги восстановления:

  1. Импорт из VMware в OVF — строго через .vmx (чтобы сохранить кластерную конфигурацию), без конвертации дисков в .vdi. Это позволило обойти привязку к оборудованию за счёт использования стандартных драйверов проблемных устройств.
  2. Подключение новых OVF в VirtualBox — система загрузилась, но MAC-адреса изменились, что вызвало повреждение сети.
  3. Ручное восстановление MAC-адресов — повторное прописывание требуемых MAC в менеджере виртуальных машин. После этого конфигурация перестала «ломаться».
  4. Правка сетевых конфигов — в файле /etc/network/interfaces переименован интерфейс ens160 → enp0s3 (система выборочно переименовывала подключение в двух местах конфига).
  5. Настройка клиента — исправлен файл hosts: 
    10.29.96.24   octopus.example.local
10.29.64.3    datastore.example.local
    Также назначено имя, суффикс домена и псевдоним для DataStore.
Результат: система стабильно работает длительное время. Задача «Восстановление из горячего бэкапа на новом железе» выполнена.

Восстановление доступа и функциональности

  • Права администратора — восстановлены под прежним логином без повреждения базы данных.
  • File-manager (backend) — частично функционален:
    • ✔ Метод Get (просмотр файлов через браузер) — работает.
    • ◐ Метод Post/Put (загрузка файлов) — не выгружается в систему, требуется API с инструкциями для базы.
    • ✘ Метод Mkcol (создание папок) — без удалённого модуля невозможно. Через консоль работает частично, POST блокируется на уровне ядра.
    • ◐ Метод Delete — удаляет не всё.

Выяснено, что полноценное выкладывание данных (особенно результатов расчётов) работает только с рабочего стола расчётного модуля. Для нормального режима требуется дистрибутив; администратору системы предложено создать виртуальный образ действующего сервера.

Невыясненные вопросы

  • Скриптовая система на сервере присутствует, но полное удаление невозможно — «разваливается» кластер. Оставлена для проверки на стабильность.
  • Иногда включается iptables, и сервер закрывается от backend — причина не установлена (правила с текстовика не грузятся).
  • В сетевой конфиг явно что-то вмешивается (прячется кэш) — возможно, при импорте в систему «ныряет» необнаруженное устройство.
  • Исправлено: сервер доступен постоянно; кэш больше не мешает.

Итоги

Проект продемонстрировал, что стандартные методы миграции неприменимы к системам со скрытой аппаратной привязкой. Обход защиты через импорт конфигурации .vmx в VirtualBox и ручную правку сетевых параметров позволил восстановить работоспособность кластера без потери данных — именно за счёт использования возможностей, которых не существовало на момент создания системы.

Работа законсервирована для возможности повторения в будущем. Следующий этап — создание чистой версии системы для распространения и полноценная настройка File-manager.
